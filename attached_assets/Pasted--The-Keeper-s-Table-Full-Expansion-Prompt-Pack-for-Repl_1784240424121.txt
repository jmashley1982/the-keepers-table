## PHASE 1 — Campaign-Context-Aware AI (the retrieval layer)

```
[paste GLOBAL CONTEXT here]

TASK: Make every Claude API call in the app campaign-aware. Right now, generation requests (Quick Generate, Generate NPC, Gen Encounter, Gen Treasure, Generate Foe, Prep Next Session suggestions) appear to send only the user's immediate request. I want them to automatically include relevant campaign context so outputs are consistent with my world.

1. BUILD A CONTEXT ASSEMBLY SERVICE
- Create a single server-side function, e.g. buildCampaignContext(campaignId, options), that assembles a context block containing:
  a. Campaign basics: name, system (e.g. Dungeon World), and the Session Zero / campaign planning notes.
  b. Entity summaries: name, type, one-line description, and status tags for all NPCs, factions, locations, and plot threads (or the most recently active N of each if the campaign is large — make N configurable, default 25 per type).
  c. Recent session notes: full text of the last 2 wrapped sessions' notes plus the current live session's notes, with entity tags rendered as readable names.
  d. The party: each PC's name, class, level, and player name.
- Include a rough token budget guard: if assembled context exceeds a configurable character limit (default ~12,000 characters), truncate oldest session notes first, then trim entity lists to the most recently referenced entities (use tag mentions in session notes to rank recency).
- Every existing Claude API call site must be refactored to prepend this context block to its system prompt or user prompt. Do this as a shared wrapper so future AI features get it for free.

2. RELEVANCE BOOSTING
- If the user's generation request mentions an entity by name (case-insensitive match against the campaign's entity names), include that entity's FULL description and status, not just the one-liner.

3. UI TOUCHES
- In the Quick Generate modal, add a small toggle: "Use campaign context" (default ON) with a tooltip explaining that generations will reference existing NPCs, factions, locations, plot threads, and recent sessions.
- Add a subtle indicator on generated results when context was used (e.g., a small "campaign-aware" chip).

4. TESTING
- Add one test/dev route or script that prints the assembled context for a given campaign so I can inspect exactly what's being sent to Claude.

Do not change any generation prompts' creative instructions — only add the context layer. Confirm the shape of the context block with me before wiring it into all call sites.
```

## PHASE 3 — Relationship Web + Plot Thread Lifecycle

```
[paste GLOBAL CONTEXT here]

TASK: Two related features: an explicit relationship graph between entities, and a lifecycle for plot threads.

PART A — RELATIONSHIP WEB
1. Schema: a relationships table: (campaign_id, from_entity, to_entity, relationship_type, label, notes). Relationship types: ally, enemy, family, member_of (NPC→faction), rules (NPC→location), owes_debt, knows_secret, romantic, rival, custom.
2. UI: On every entity detail page (from Phase 2), a "Relationships" section listing edges with the other entity's portrait chip; add/edit/remove inline.
3. GRAPH VIEW: A new "Web" tab inside the Library: an interactive force-directed graph of all campaign entities and their relationship edges. Nodes colored by entity type, edges labeled by relationship type. Clicking a node opens the entity panel. Filter controls: by entity type and relationship type. Use a lightweight library (e.g., d3-force or cytoscape.js) and keep it performant up to ~200 nodes.
4. AI SUGGESTIONS: A "Suggest connections" button that sends the entity list + descriptions + recent session notes (via the Phase 1 context service) to Claude and asks for 3–5 plausible relationship edges with one-line justifications. Each suggestion renders as a card with Accept / Dismiss. Accepting writes the edge.

PART B — PLOT THREAD LIFECYCLE
1. Add a status field to plot threads: dangling (default), active, resolved, abandoned. Show status as a colored chip; filterable in the Library's Plot Threads tab.
2. On session wrap (hook into the existing Wrap Session flow), send the session's notes + the campaign's non-resolved plot threads to Claude and ask it to identify which threads were advanced or resolved. Render results as suggestion cards: "This session seems to advance [thread] — mark active? / resolved?" with Accept / Dismiss. Never auto-change status without user confirmation.
3. The Dashboard's "Prep next session" feature must be updated to explicitly draw from dangling and active threads (pass them in the context with their statuses).

Confirm both schemas with me before building UI.
```

```
TASK: When a GM wraps a session, automatically generate two recap artifacts.

1. WRAP FLOW
- Extend the existing Wrap Session flow: after confirming the wrap, show a "Generating recaps…" state, then a review screen with two tabs:

3. PLOT THREAD INTEGRATION
- Run the Phase 3 plot-thread suggestion pass as part of this same wrap flow, on the same review screen (third tab: "Threads"), so wrapping a session is one unified ritual: recap for players, debrief for me, thread updates.
```

## PHASE 5 — Encounter Runner, Dice & Oracle

```
[paste GLOBAL CONTEXT here]

TASK: Tools for running combat and improvising at the table, integrated into the Live Session view.

PART A — ENCOUNTER RUNNER
1. In the Live Session view, add an "Encounter" panel (toggleable, alongside session notes — do not replace the notes; GMs need both visible on desktop).
2. Starting an encounter: pick an existing Encounter from the Library, generate one (Gen Encounter, campaign-aware via Phase 1), or build ad hoc by searching the Bestiary and adding monsters.
3. The runner tracks a combatant list: PCs (pulled from Players) and monsters (from Bestiary or custom). For each combatant: name, current/max HP with quick +/- adjustment, and free-text condition tags (e.g., "prone", "burning"). Support duplicate monsters with auto-numbering (Goblin 1, Goblin 2).
4. Turn order: a simple drag-to-reorder initiative list with a "next turn" button that highlights the active combatant and tracks round number. Keep it system-agnostic — no auto-rolled initiative, since Dungeon World doesn't use it, but allow manual ordering for systems that do.
5. Clicking a monster shows its full stat block from the Bestiary in the panel.
6. When a monster hits 0 HP, offer one-click "mark dead" which strikes it through. On encounter end, offer to append an auto-generated one-line summary to the session notes (e.g., "⚔ Encounter: party defeated 3 goblins and a hedge wizard at The Tavern") with entities tagged.

PART B — DICE ROLLER
1. A compact dice tray in the Live Session view: buttons for d4, d6, d8, d10, d12, d20, d100, custom formula input (e.g., 2d6+1), roll history for the session. Client-side rolls are fine.

PART C — GM ORACLE & RANDOM TABLES
1. Oracle: an input in the Live Session view where the GM types a yes/no or open question ("Would the guard take a bribe?"). The app rolls 2d6 internally, then sends the question + roll result + campaign context (Phase 1) to Claude with instructions to interpret: 10+ = yes and, 7–9 = yes but, 6- = no and — with a one-sentence in-fiction consequence. Show the roll and the interpretation.
2. Random tables: a "Tables" section under Tools. GM can generate campaign-flavored tables via Claude (rumors, random encounters by region, weather, tavern patrons, names) — each table is 12 or 20 rows, stored, rollable with one click, and editable. Seed each campaign with a "Rumors" table generated from campaign context on first visit.

Build Part A first and check in with me before B and C.
```

```
4. LIVE SESSION INTEGRATION
- The Live Session view's Map tab (already present in the entity tag bar) opens the interactive map inline, with fog controls if it's a battle map, so the GM can run everything from one screen.
```

```
1. PORTAL ACCESS
- Per campaign, the GM can generate a player invite link. 4. GM CONTROLS
- Campaign Settings gains a "Players & Portal" section: view/revoke invite link, see joined players, remove a player, toggle portal features on/off.
```

## GENERAL TIPS FOR RUNNING THESE IN REPLIT

1. **One phase per agent session.** Fresh context per phase avoids the agent forgetting constraints.
2. **Always let it propose schemas first.** Every phase says "confirm with me" — hold it to that. Schema mistakes are the expensive ones.
3. **Test the sharp edges yourself:** the anonymous safety-tool storage (Phase 7), public share links being truly unguessable and read-only (Phases 4, 6, 7), and the context service not leaking GM-only info into player recaps (Phase 4).
4. **Watch API costs.** Phases 1 and 4 increase Claude token usage substantially (context blocks + recap generation). Consider caching the assembled context per session and only rebuilding when notes change.
5. **Commit/checkpoint between phases** so you can roll back a bad phase without losing the previous ones.
